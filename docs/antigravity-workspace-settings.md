# Bounded Antigravity Workspace Settings (Headless Research)

Status: **implemented, disabled by default** (issue #826; reconciled with the
installed `agy` 1.1.9 by issue #830).

Follow-up child of #802; builds on #804, #805, #806, #813, and #814.

---

## 0. Purpose

The constrained headless Gemini research path from #802–#806 still fails on a
repository-backed research task:

```text
outcome: permission-denied/read
no output produced - a tool required the "read_file" permission that
headless mode cannot prompt for, so it was auto-denied.
```

The Antigravity application and the headless `agy` CLI do not share interactive
approval state. `agy` reads exactly two settings layers:

1. `~/.gemini/antigravity-cli/settings.json` (global)
2. `<workspace_root>/.gemini/settings.json` (workspace)

Only the filename `settings.json` is recognized; there is no automatic
`settings.local.json` layer. A research run whose workspace has no permission
configuration therefore auto-denies the first tool call and produces nothing.

> **Correction (issue #830).** #826 put the permission rules in the *workspace*
> layer only. Against the installed `agy` 1.1.9,
> that layer is not consulted for a headless tool request, so the run still
> failed with `permission-denied/read` while the runner reported its profile
> prepared and verified. Two assumptions were wrong and are fixed here:
>
> 1. **Where the rules live.** Bounded permission rules are
>    installed into the **global** settings file for the duration of the run
>    (§2.5), which is the layer the CLI actually applies. The workspace
>    document is still generated and still bounds the tool set, but it is no
>    longer the only grant.
> 2. **How trust is represented.** The CLI records trust as
>    `trustedWorkspaces: ["<path>"]`, not `trustedFolders: {"<path>":
>    "TRUST_FOLDER"}`. An already-trusted workspace read as untrusted (§3).
>
> The pin that let both slip through untested is closed by §6.3: the installed
> CLI's version is probed and gated before anything is written, and a bounded
> real-CLI smoke test (§11.1) exercises the installed binary rather than a
> stand-in.

This document specifies the minimal, runner-owned preparation step that lets a
headless research run enumerate, read, and search its own repository without
enabling writes, commands, child processes, or any broad global grant.

> **Boundary summary.** The permission profile decides what the *CLI* will do
> without prompting. It never decides what the runner *serves into the prompt*
> or *publishes* — that stays with the evidence resolver
> (docs/research-evidence-contract.md), which this layer may not widen. See §10.

## 1. Runner-owned generation (normative)

- The file is generated by trusted orchestration code
  (`src/handlers/antigravity-workspace.ts`, driven by
  `src/core/antigravity-workspace-settings.ts`), immediately before the agent is
  started. It is never produced by an npm lifecycle script, a repository-owned
  helper, or anything the agent or the Issue body can influence.
- The exact research workspace root is resolved first, through `realpath`, and
  every path-bearing rule is scoped to that resolved root. A symlinked workspace
  root is scoped to its real path, never to the link's parent.
- Repository-provided settings are **never** read, merged, or consulted. The
  runner writes the complete permitted configuration for the run; any
  pre-existing file — stale runner output, a malformed document, or a
  repository-authored one — is replaced whole.
- The file is regenerated before **every** headless invocation, including every
  evidence turn (#806 re-invokes the agent per turn), so a previous run or a
  previous turn can never persist a broader profile into the next one.
- The generated file must be Git-ignored and must not produce a tracked or
  untracked dirty-worktree result (§7).
- The write is **contained by descriptor**, not by a path check. `O_NOFOLLOW`
  on `settings.json` protects only its final component, so a `.gemini` swapped
  for a symlink after the path checks would otherwise redirect the write outside
  the workspace. Preparation therefore opens `.gemini` itself with
  `O_NOFOLLOW | O_DIRECTORY`, records that directory's `dev`/`ino`, opens the
  settings file **without** `O_TRUNC`, and only truncates and writes once the
  directory still resolves to the pinned inode and the opened descriptor is the
  same file the path names. A swap either way is refused with nothing outside
  the workspace touched. The read-back reads that same descriptor, so it
  verifies the bytes at the inode that was written rather than whatever the
  path resolves to afterwards. Node has no `openat`, so the `O_CREAT` step
  cannot be made fully atomic; the pin is re-checked immediately before it, and
  the residual window can only ever create an empty file, never disclose or
  destroy content.
- The **pathname is re-verified at launch**, as the last step before the CLI is
  started. Descriptor containment proves what was written, but `agy` resolves
  `<workspace>/.gemini/settings.json` itself at startup, so anything able to
  write inside the workspace in between could rename the generated file away and
  leave a broader regular file at that name. Verification therefore re-resolves
  the root and `.gemini`, re-opens the file with `O_NOFOLLOW`, and compares its
  size and content hash — read from that descriptor — against the generated
  profile. A mismatch is `settings-replaced-before-launch`; it is never repaired
  in place, because the safe response to an unexplained profile is to refuse.
  This runs before every invocation, including every evidence turn. Since #830
  it covers the global overlay too: the run's journal must still be there and
  every rule it claims must still be installed, or the launch is refused with
  the same reason — the grants the CLI will actually apply are verified, not
  only the document in the workspace.
- The profile is **built and validated before anything is mutated**. Its
  refusals (`operator-glob-budget-exceeded`, `rule-budget-exceeded`,
  `workspace-root-unrepresentable`, `schema-drift`) are configuration errors, so
  they must not leave a persistent trace: they fail before the trust store is
  written and before the runner-owned `info/exclude` entry is appended.
- The **installed CLI is version-gated first** (§6.3), before any file is read
  or written, so a build whose configuration loading this document was never
  reconciled against never reaches the write path.
- The same rules are installed into the **global** settings store, which is the
  layer the CLI applies (§2.5), and so is the **read-only tool registration**
  that decides which tools exist for the model to select at all (§2.6). That
  installation is the last mutation preparation makes, it is locked and
  journalled, and it is removed again on every exit path.

## 2. The generated document

Policy identity, recorded in the local artifact:

| Field | Value |
|---|---|
| `policyVersion` | `research-readonly/3` |
| `schemaPin` | `antigravity-cli/settings@3` |
| `relativePath` | `.gemini/settings.json` |
| supported CLI | `>=1.1.9 <2.0.0` (§6.3) |

Shape (rendered with two-space indent and a trailing newline, so the same policy
always hashes identically):

```jsonc
{
  "permissions": {
    "allow": ["read_file(<workspace_root>)", "read_file(<workspace_root>/**)", "…"],
    "deny":  ["run_shell_command", "write_file", "read_file(<workspace_root>/**/.env)", "…"]
  },
  "tools": {
    "core":    ["glob", "list_directory", "read_file", "read_many_files", "search_file_content",
                "GlobTool", "GrepTool", "LSTool", "ReadFileTool", "ReadManyFilesTool"],
    "exclude": ["google_web_search", "replace", "run_shell_command", "save_memory", "web_fetch", "write_file",
                "EditTool", "MemoryTool", "ShellTool", "WebFetchTool", "WebSearchTool", "WriteFileTool"]
  },
  "coreTools":    ["… identical to tools.core …"],
  "excludeTools": ["… identical to tools.exclude …"],
  "autoAccept": false,
  "mcpServers": {}
}
```

Only the keys listed above may appear. `autoAccept` is always `false` and
`mcpServers` is always empty: the profile grants named, path-scoped read-only
tools and nothing else, and `--dangerously-skip-permissions` is never passed.

The `tools` lists carry each tool under both spellings the schema accepts — the
tool name and the implementing class name — and the same registration is
repeated under the legacy `coreTools` / `excludeTools` keys, for the reasons in
§2.6. The two registrations are generated from one pair of lists and a document
whose copies disagree is refused as drift. The permission rules stay on the tool
names alone.

## 2.5 The runner-owned global overlay (issue #830)

`agy` 1.1.9 applies permission rules from the **global** settings file, so that
is where the grants have to be installed for the run to work at all. Doing this
to a file full of unrelated user configuration is the delicate part of this
layer, and it is bounded as follows.

**What is installed.** Only *path-scoped* rules, all derived from the same
generated profile: every allow rule (each scoped to the exact resolved workspace
root and its subtree) and every path-bearing deny rule (the evidence deny floor
and the operator globs, scoped the same way).

**Why both the directory and the subtree rule.** Each tool is granted twice —
`read_file(<workspace_root>)` and `read_file(<workspace_root>/**)`. The CLI
documents a directory target as covering the files below it, in which case the
first rule suffices and the second is redundant; if instead a rule matches
literally, the second is the one that grants the subtree. Emitting both means
the grant is exactly the workspace under either reading, and neither rule
reaches outside it.

**What is deliberately not installed.** The unscoped, tool-name-only deny rules
(`run_shell_command`, `write_file`, …) stay in the workspace document. A global
unscoped deny would change the CLI's behaviour for *every other workspace on the
machine* while a research run is in flight — a side effect on unrelated user
configuration, which this layer does not take. Nothing is weakened by omitting
them: the overlay grants no write, edit, command, child-process, network,
credential, or memory tool at all, and headless `agy` denies what is not
allowed.

**What is suspended.** Every `allow` rule the operator already had, for the
lifetime of the overlay. The global layer is the one the CLI applies, so a rule
sitting in it is a capability *of the research invocation* — an operator who
allows `run_shell_command`, a write tool, or a path outside this workspace would
otherwise hand a supposedly read-only run the ability to execute commands or
mutate the repository, and the workspace document cannot take it back because
that is precisely the file `agy` ignores. The rules are therefore lifted out,
recorded in the journal, and restored verbatim — in the order they were found —
by the last overlay to release. The temporary change is fail-closed in the only
direction that matters: another process on the machine sees *fewer* grants while
a research run is in flight, never more. Rules another live overlay installed
are not the operator's and are left in place. A rule the operator listed more
than once is recorded and restored with the same multiplicity, so a store that
repeats a grant is not quietly collapsed to a single copy.

**What is preserved.**
Every unrelated key, every unrelated rule, and their order: the `deny` list, and
any other list such as `ask`, are untouched throughout, and the suspended
`allow` rules go back exactly as found. The runner's rules are appended to the
existing lists, never merged into them, never reordered around them, and never
deduplicated against them. The document is re-rendered with the indentation and
trailing newline it was found with — and a store written on one line stays
minified rather than being expanded — so an untouched store
comes back byte-for-byte once the entries are released. Where re-rendering
*cannot* reproduce the bytes an operator wrote (escaped non-ASCII, spacing no
serialiser produces), the installation records the store's original bytes in its
journal and writes them back verbatim the moment the document is semantically
back to them; the recorded copy is carried forward by a run that reclaims a
crashed one *and by a second run on the same workspace*, whose co-tenant may
otherwise release first and take the only copy of those bytes with it, and it is
written `0600` beside the store it copies and removed with the overlay. Nothing is recorded when the store renders back to itself,
which is the ordinary case. A store that does not
parse as JSON is never repaired or replaced (`trust-store-unreadable`).

**Lifecycle.** Installation is the *last* mutation preparation performs, so
every refusal above it leaves the global store untouched. Removal happens on
every exit path — success, refusal, and agent failure — before the run reports
anything, and a removal that does not succeed **fails the phase**
(`global-overlay-release-failed`). It is not a local footnote: the entries are
machine-wide read grants, and the journal naming them carries the worker's
long-lived pid, so nothing else on the machine treats them as abandoned while
that worker is running and every `agy` invocation sharing the store inherits
them in the meantime. The removal is retried before the phase gives up (transient lock
contention is the usual cause), the underlying reason is recorded in the local
artifact as `releaseFailure`, and the next preparation in that process supersedes
the leaked journal.

**One workspace at a time.** Two research workspaces never hold grants in the
store simultaneously. The permission set is global: whatever is installed while
an agent runs is what *that* agent may do, so an overlay live for workspace B
would let workspace A's agent read B's tree by absolute path — the exact-workspace
boundary this layer exists to draw. The store lock cannot express that (it is
held for a read-modify-write, not for the agent's whole lifetime), so the
journals do: installation waits while a live journal names a *different*
workspace and refuses with `global-overlay-contended` if it never releases.
Waiting long is pointless — a headless invocation runs for minutes — so the wait
is short and the phase is simply retried later. Two runs on the *same* workspace
are co-tenants, not contention: their scope is identical, and each rule is
released with the last claim on it. The launch-time check enforces the same
boundary at the moment it matters: an `allow` entry no journal *for this
workspace* claims fails the run closed (`settings-replaced-before-launch`).

**Concurrency.** Every read-modify-write of the store (trust registration,
overlay installation, overlay removal) runs under an advisory lock beside the
store (`settings.json.n8n-ai-cli-loop.lock`, `O_CREAT | O_EXCL`), and the store
itself is replaced by an atomic rename, so a concurrent reader — including `agy`
— sees the old or the new document, never a partial one. A lock whose holder is
*demonstrably gone* — a dead pid, or, only when the file names no pid at all, an
mtime older than 60s — is taken over so a crash cannot wedge later runs. A live
holder keeps the lock however long its critical section runs: a slow write is
waited on and then refused (`global-settings-locked`), never interrupted, since
evicting it would admit a second writer. Each holder writes a token into the
lock and removes it on release only while that token is still its own, so a
holder that was declared abandoned cannot delete its successor's lock.

Taking a lock over is itself tied to the file that was inspected, because two
contenders can reach the same "abandoned" conclusion and the loser's unlink
would otherwise delete the lock the winner had already replaced it with —
putting both inside the critical section. A short-lived marker
(`…lock.takeover`, `O_CREAT | O_EXCL`) makes at most one process eligible to
unlink at a time, and inside that window the path is re-inspected and left alone
unless it still names the inspected dev/ino. A marker outliving its owner (a
crash inside those few syscalls) ages out, so reclaim cannot be wedged
permanently; only the takeover of an already-abandoned lock is delayed.

**Crash safety.** Each installation writes a runner-owned *journal* beside the
store (`n8n-ai-cli-loop-overlays/<key>.json`) recording exactly which rules it
added, which of them were already the operator's (`foreign`, never removed),
which of the operator's `allow` rules it suspended, and whether the
`permissions` containers existed beforehand. Removal deletes only rules this run
added that no other still-installed overlay claims, and restores the suspended
rules and the original container shape when the last claim is gone. Removal is
**counted, not matched by identity**: an overlay adds one copy of each rule it
did not already find, and one copy is all it takes back out, so an identical
workspace-scoped rule the operator writes into their own store mid-run — not
`foreign`, because it was not there at installation — survives the release. A
journal is only ever deleted once the state it describes is gone: a superseded journal
survives until its replacement journal *and* the new store are both written, so
a failed turn can never leave installed grants that nothing claims. The next run to take
the lock reclaims any journal whose owning process is gone or whose workspace no
longer exists — so a killed run's grants do not survive it; a reclaimed journal
is likewise settled only *after* the store update carrying its revert commits, so
a preparation that fails before that write leaves the claim intact for the next
pass instead of orphaning the rules it names. **Age is not
liveness**: an overlay whose owner is still running is never reclaimed, however
long it has been installed, because a research run that outlives any timeout the
runner picked is still an agent operating under those rules and stripping them
would hand the shared permission set to another workspace mid-run. The 12-hour
TTL only *reports*: a blocker past it is named in the `global-overlay-contended`
refusal as a possibly-recycled process id, with the journal file to remove, so
the one case where the owning pid can lie is actionable rather than permanent.
A preparation also supersedes every journal its *own* process still
owns — the next turn on the same workspace, and any overlay a failed release
leaked — so a long-lived runner holds at most one journal at a time and its own
pid can never make a leak look live.

**A journal that cannot be deleted is retired, never abandoned.** Removing the
file is normally how a claim ends, but an ACL or an immutable flag can refuse the
unlink mid-run, and a leftover journal carrying this process's pid would keep
reading as live for as long as the worker runs — a phantom claimant that blocks
other workspaces and makes the run's own release hold rules in place for a claim
nobody owns while still reporting a clean release. Such a journal is therefore
rewritten as `retired`: it still names its rules, so they stay reclaimable, but
it is no longer live, so nothing waits on it and nothing is held for it. A
superseded journal is retired *before* the replacement is written (the record
survives the write window either way, so the guarantee above is unchanged).
Retiring is the floor, not a best effort: a superseded journal that resists even
the rewrite fails the installation closed with nothing written
(`global-settings-write-failed`), and a run whose own journal can be neither
removed nor retired fails its release closed
(`global-overlay-release-failed`) rather than reporting a release it could not
complete. A launch-time check that finds this run's journal retired refuses the
same way a removed one does. A journal retired *after* its entries are already
back out of the store — a completed release, or an installation whose store
write never landed — is additionally marked `settled`, and a settled journal is
only ever deleted, never reverted a second time: the removal is what failed, not
the release, and re-applying it would take out a matching workspace-scoped rule
the operator has added since.

A journal is installed by an atomic rename of a temp file (not named `.json`, so
an in-flight write is never mistaken for a journal) whose bytes are `fsync`ed
first, so the record is whole and durable *before* the store update it describes
can be. A journal that nonetheless cannot be parsed — or whose `claim`,
`foreign`, `containers`, or suspended-`allow` shape is not one the revert path
can act on — is **never** treated as absent: it may name rules that are
installed right now, and discarding it would discard the only handle by which
they could ever be removed (the 12-hour TTL is read *from* the journal, and it
reclaims nothing anyway). Installation therefore refuses
(`global-overlay-journal-damaged`) with the offending file *name* in the local
diagnostic (never its path, §8), leaves the file on disk for the operator, and
installs nothing further; a launch-time check that finds one refuses the same way
`settings-replaced-before-launch` does. Release still removes *this* run's
entries — a damaged peer only suppresses the last-overlay-out restoration of the
operator's suspended `allow` rules, which is the fail-closed direction — unless
the damaged journal is this run's own, which is reported rather than silently
counted as released.

**Symlinked stores.** An operator whose dotfiles are a repository commonly
symlinks the global settings file elsewhere. The atomic rename would replace the
*link*, so the store's pathname is resolved first and the write goes to its
target; the link survives every mutation. A link to anything but a regular file,
or one whose target cannot be resolved, is refused
(`global-settings-write-failed`) rather than created or guessed at. Containment
(§3.4) is already checked against the fully resolved path, so a link pointing
back into the research workspace is rejected before any of this runs.

## 2.6 The read-only tool surface (issue #832)

§2.5 got the *grants* into the layer the CLI reads, and the acceptance run still
produced nothing. The observed failure was not a denied read: the CLI registered
its full default tool set, the model selected a command/process tool, headless
mode auto-denied it because it cannot prompt, and the run ended with an empty
report and `permission-denied/command`.

A permission rule is the wrong instrument for that. It answers "may this tool act
here?" *after* the model has already spent its turn choosing the tool. What has
to change is which tools exist to be chosen, and that is decided by the
registration keys — which, like the rules, are only honoured from the global
store.

**What is installed.** The non-permission half of the same generated profile,
written into the global store alongside the rules and journalled with them:

| Key | Installed value | Why |
|---|---|---|
| `tools.core` | the read-only tools, every spelling | a *positive* list: a tool not named here is not registered, whatever the build calls it |
| `tools.exclude` | the write/edit/command/network/memory tools, every spelling | defence in depth behind the positive list |
| `coreTools` / `excludeTools` | identical to the two lists above | the legacy spelling of the same pair; which one a build reads is what this issue could not settle on-host |
| `mcpServers` | `{}` | a subprocess-backed tool source a `tools.core` list does not reach |
| `autoAccept` | `false` | would approve whatever a tool asks for, without a prompt |

Emitting both key spellings is deliberate and costs nothing: they are generated
from one pair of lists, a build that knows only one ignores the other, and the
failure mode of guessing wrong is a run with *no* tools — which fails closed and
is visible — rather than one with a shell. That failure has a shape worth naming:
a build whose registration vocabulary this section has wrong registers nothing
the runner asked for, so the run exits 0 with no findings and is classified
`empty-output`. An `empty-output` research run on a profile-enabled session is
therefore the second thing to check against the installed CLI, after the
`permission-denied/command` case below; `research-workspace-settings.json`
records the exact registration that was installed.

**Naming, and why both spellings.** The working diagnosis for #832 allowed that
the installed build might call its command tool something other than
`run_shell_command`. The positive list makes that question moot — an unnamed
tool is not registered regardless of its name — and the lists carry the class-name
spelling as well (`ShellTool`, `ReadFileTool`, …) because this schema has always
accepted both. The asymmetry is what makes that safe: an `exclude` entry matching
no tool is inert, so an unused spelling costs nothing while a *missing* one would
leave a command tool registered; a `core` entry matching no tool registers
nothing, so the extra spellings widen the surface by exactly zero tools. The pinned
command-capable spellings (`COMMAND_CAPABLE_TOOL_NAMES`) have their own regression
test, and a profile that names one of them in `core`, or omits one from `exclude`,
is `schema-drift` rather than a profile.

**What is suspended, and the side effect that is accepted.** The operator's own
`tools`, `mcpServers`, and `autoAccept` values are lifted out for the overlay's
lifetime and restored, verbatim, by the last overlay to release — the same
mechanism, journal, and last-one-out rule as the suspended `allow` rules (§2.5).
Unlike the unscoped deny *rules*, which stay in the workspace document, this does
change what tools a concurrent `agy` invocation on the same machine has while a
research run is in flight. That is accepted deliberately: the change is strictly
*narrowing* (fewer tools, never more), the store already carries one workspace's
overlay at a time, and the alternative is a research run that keeps selecting a
tool it can never be granted. A key that something else rewrote during the run is
left exactly as it stands rather than overwritten with a stale value.

"Last out" is counted over the overlays that actually *hold* the surface, which is
not the same set as the live permission claims. A journal written before this
section existed carries rules but no surface record: it installed no registration
and its own release can restore none, so a run that deferred to it would leave the
read-only registration in the operator's store with nothing able to remove it, and
later runs would read it as configuration they must preserve. During a rolling
upgrade — the one window where such an overlap happens — the newer run therefore
releases the surface itself. A journal too damaged to read is the unknown case and
still defers, because a live run may be relying on the registration. For the same
reason a surface record must account for every suspended key, exactly once, with
the value installed for it: a well-formed but incomplete record would verify
nothing at launch and restore nothing at release, so it is treated as a damaged
journal (§2.5) rather than as "no surface".

**And not handed over when it no longer matches.** Two runs on the *same*
workspace are co-tenants (§2.5), and the later one inherits the operator's
surface values from the earlier one's journal rather than re-reading a store that
already carries the runner's registration. That is only faithful while the store
still holds what a live overlay installed: a key edited in between belongs to the
operator and is recorded nowhere, so installing over it would leave whichever run
releases last restoring the value from before the edit — the opposite of the
preservation above. Such an installation is *refused*, and waits, rather than
taking the handoff. Backing off is what preserves the edit: the co-tenant's own
release leaves the key it no longer recognises exactly as found, and the retry
after it records the operator's real values. A wait that never clears fails the
run closed with `global-overlay-contended`, naming the changed keys and the
journal still holding them.

**Verified at launch, like the rules.** The pre-invocation check compares each
installed surface key against what the journal recorded; a `tools`, `mcpServers`,
or `autoAccept` value that changed after preparation refuses the launch with
`settings-replaced-before-launch`, because the agent would otherwise start under
a tool set the runner cannot state.

**Stated in the prompt as well.** The runner-owned research prompt names the
five read-only tools and prohibits command, process, write, and network attempts,
so an agent that would otherwise spend its run reaching for a shell routes around
it instead. This text is composed by the runner and sits in the Instructions
section, after the delimited Issue body: untrusted Issue text never defines this
boundary. The prompt is guidance; the registration above is the enforcement.

**When a supported CLI does not honour it.** A `permission-denied/command`
outcome on a run that installed the registration is a compatibility finding
about the installed build, not an ordinary denial. It is recorded as
`research-tool-surface-violation.json` — the policy identity, the CLI version, the
exact registration installed, the pinned command-capable spellings, and the
operator's next step — and the public failure string says the pin has to be
re-verified against the installed CLI. Granting `run_shell_command`, adding a
shell allowlist, widening the allow rules, or passing
`--dangerously-skip-permissions` is never the remedy: research runs read-only by
contract.

## 3. Workspace trust

### 3.1 Verification

Trust lives in the global settings document, in one of two representations. Both
are read; only the first is ever written.

| Container | Shape | Written? | Grants |
|---|---|---|---|
| `trustedWorkspaces` | array of absolute paths | yes | **exact** entry only |
| `trustedFolders` (legacy) | map of absolute path → status | never | `TRUST_FOLDER`, ancestor `TRUST_PARENT` |

`trustedWorkspaces` is what `agy` 1.1.9 writes and reads; #826 assumed the
legacy map alone, which made an already-trusted workspace read as untrusted and
sent the runner registering an entry the CLI was not consulting. The legacy map
keeps its pinned status vocabulary — `TRUST_FOLDER` (this exact folder),
`TRUST_PARENT` (this folder and its descendants), `DO_NOT_TRUST` — so an
operator's existing store keeps working. An unrecognized status value, or a
`trustedWorkspaces` that is not an array of strings, is schema drift and fails
closed (§6.2).

The evaluation is exact-first, and distrust wins wherever it appears. An
**ancestor** entry in `trustedWorkspaces` is deliberately *not* read as trust:
the array form carries no status literal saying "and everything below it", so
inferring one would be exactly the broad parent grant this layer refuses to lean
on — the workspace is registered in its own right instead. The legacy map's
`TRUST_PARENT` on an ancestor stays recognized, because the CLI itself applies
it. An explicit `DO_NOT_TRUST` on the workspace refuses the run.

### 3.2 Registration

Registration is opt-in (`registerTrust`, default `false`); without it an
untrusted workspace fails closed with an actionable local diagnostic instead of
being silently granted.

When it is enabled the runner writes **only** the exact workspace path, appended
to `trustedWorkspaces`. It never writes a parent-directory entry, never widens
an existing entry, never duplicates one, never writes to the legacy container,
and preserves every unrelated key and every unrelated trust entry in the global
document. The write takes the store's lock and re-reads the document inside it
(§2.5), so a concurrent run's registration or overlay is never clobbered — and
it re-evaluates trust against that locked document before writing anything, so a
revocation that lands between the first read and the lock still refuses the run
(`workspace-distrusted`) instead of being overwritten by the registration.
Distrust wins wherever it appears (§3.1), including when it appears late. If the
locked document already trusts the workspace — another run registered it in that
window — the entry is left exactly as written and nothing is added.

A workspace that was **already** trusted skips registration, and with it that
lock, so the last word belongs to the overlay installation (§2.5): it
re-evaluates trust against its own locked document and refuses before installing
anything — `workspace-distrusted` when the operator wrote an explicit
revocation, `workspace-not-trusted` when they simply withdrew the grant and left
the workspace untrusted. A trusted parent still passes, exactly as it does on the
first read. A revocation or withdrawal that lands
between the first, unlocked read and the moment the permission entries go in
therefore refuses the run rather than being quietly preserved beside a
successful preparation. A
global settings file that cannot be parsed is never replaced or repaired —
unrelated user settings live there — the run fails with
`trust-store-unreadable`.

### 3.3 Stale trust entries

A trust entry is **stale** when its recorded path no longer resolves to an
existing directory — the usual cause is a deleted clone or a removed per-issue
worktree. Stale entries are identified with `findStaleTrustEntries`, which takes
the parsed global document and a directory-existence probe and returns the
recorded paths that no longer exist, sorted, across **both** containers.

Removal is a deliberate operator action, never automatic: a path that is merely
unmounted or temporarily detached is not a revocation. To clean up, list the
stale entries, confirm each one is genuinely gone, and rewrite the global
document with `withoutTrustEntries`, which drops exactly the listed keys and
preserves all other settings. Re-running research after cleanup re-verifies
trust and, with `registerTrust` enabled, re-adds only the exact workspace in
use.

### 3.4 The store must live outside the workspace

The global store's location is refused (`trust-store-inside-workspace`) when it
resolves inside the research workspace — whether it came from
`globalSettingsPath`, from `ANTIGRAVITY_CLI_SETTINGS`, or from the default.

The generated profile grants `read_file` over the whole workspace, so a store
placed under it would be readable by the headless agent: trust entries for other
repositories and unrelated user settings disclosed through the very boundary
this layer draws. Where the store *is* `<workspace>/.gemini/settings.json` the
two also collide outright — opt-in registration would write the trust document
to the exact path the workspace profile then overwrites, so trust would never
persist.

The check runs before the store is read, so a misplaced store is never opened
and (with registration enabled) never written. Containment is evaluated on the
resolved path: the store itself when it exists, otherwise its nearest existing
ancestor with the not-yet-created components re-attached, so a symlinked
ancestor cannot smuggle it back inside.

### 3.5 One resolved store, and only the one the CLI loads

The pathname is resolved to the file it designates **once**, at the top of
preparation, and every lock file, journal directory, read and write below is
derived from that single value. Two runners may otherwise name the same store
differently — one through a symlink, one through the link's target, one through
an unnormalised path — and, because the write resolves the link, mutate the same
file while serialising against *different* locks and writing journals into
*different* directories. Neither would see the other's live overlay, so both
could hold grants for their own workspace root in the one global permission set
their agents share (§2.5's exclusivity depends on this).

A run that will launch the CLI must also prepare the store that CLI **loads**:
`~/.gemini/antigravity-cli/settings.json`. Neither `globalSettingsPath` nor
`ANTIGRAVITY_CLI_SETTINGS` redirects `agy` — they only tell the *runner* where
to write — so preparing an alternate file for a real invocation would report a
verified profile while the agent ran under whatever the real store happened to
carry, or without the grant it needs. That combination is refused with
`global-settings-not-canonical`, before anything is written. Only a fixture run
may point elsewhere, and it is recognised by the one thing a real run never
does: answering the version probe by injection instead of executing the binary
(§6.3).

That canonical pathname is **re-derived at launch**, and the run refuses
(`settings-replaced-before-launch`) unless it still resolves to the store its
overlay was installed in. The pathname is commonly a symlink, and repointing it
between preparation and launch moves the store without touching a byte of the
old one: this run's journal and rules would all still be there and all still
verify, while `agy` followed the new target and ran under whatever permissions it
carried. Only a fixture run, which launches no CLI, is exempt — the same
exemption preparation makes.

## 4. The research permission profile

### 4.1 Allow rules

Exactly five read-only tools are allowed — `glob`, `list_directory`,
`read_file`, `read_many_files`, `search_file_content` — the minimum needed to
enumerate, read, and search evidence. Each is emitted twice, once for the
resolved workspace root and once for its subtree, so enumerating the workspace
never needs a broader rule. Every allow rule is path-scoped; an unscoped allow
rule is rejected as drift.

No allow rule exists for a tool that writes, edits, executes a command, spawns a
child process, mutates Git, uploads, POSTs, or reaches the network.

### 4.2 Deny rules

Deny rules state the boundary explicitly rather than relying on omission:

- Every write/execute/network tool is denied by name, so a future default-allow
  change in the CLI cannot silently re-admit it.
- The evidence deny floor (`DEFAULT_DENY_GLOBS`, contract §4.7) plus the
  session's `denyGlobs` and `generatedGlobs` are expanded into path-scoped deny
  rules for the content-surfacing tools (`read_file`, `read_many_files`,
  `search_file_content`). A recursive-prefix glob becomes two rules — the
  root-level copy and the nested copy — because one alone would leave the other
  readable.

Denies are scoped to the content-surfacing tools deliberately: `glob` and
`list_directory` return path names, not file bytes, and expanding every glob
across every tool multiplies the rule count without changing what content is
reachable. The rule budget (`MAX_PERMISSION_RULES`, 1024) and the operator-glob
budget (`MAX_OPERATOR_GLOBS`, 32) keep the emitted profile reviewable; exceeding
either fails closed.

---

## 5. What permission rules cannot express (accepted limitation)

`agy` permission rules are path-pattern rules. They can express *where* a tool
may act. They cannot express:

- **tracked-only scope** — the index membership test the evidence resolver
  applies (contract §4.2);
- **ignored files** — beyond what the deny globs happen to name;
- **binary content** — the sniff-and-refuse rule (contract §4.5);
- **size and line bounds** — `READ_MAX_BYTES`, `READ_MAX_LINES`, and the search
  bounds (contract §5);
- **content redaction** — the token redaction applied to served excerpts
  (contract §4.8);
- **guaranteed glob semantics** — the deny rules built from the evidence deny
  floor assume the CLI matches `**`-style patterns the way the floor means them.
  The smoke test (§11.1) verifies the *boundary* — inside the workspace is
  readable, outside is not, write/shell/network are not — but not the CLI's
  pattern engine. The deny rules are therefore defense in depth, and §5's first
  point stands: the evidence resolver, not these rules, is what bounds what a
  run may serve or publish.

Per the issue's own instruction, the response to an inexpressible boundary is to
stop and document it, not to grant a broader rule. So:

- The runner-owned evidence channel remains the **authoritative** bound on what
  repository content is served into the prompt, counted against the budgets, and
  recorded in the evidence artifacts. Nothing in this layer changes it.
- The publication rules are widened, not narrowed: **enabling this profile is
  itself a withholding condition**. With the profile enabled, with evidence
  enabled, or with an Issue body interpolated, raw agent output is withheld from
  every published comment and notification (contract §10.1) — on both the
  success path (`researchOutput` is omitted from the published context) and the
  nonzero-exit path (the excerpt is never interpolated into the failure string).
  The three conditions are ORed and none may be narrowed. The profile needs its
  own condition because it is the one that does not route content through the
  evidence resolver: a title-driven run with no body and no evidence channel can
  still read untracked, ignored, generated, or oversized files directly, so
  gating publication on the other two alone would let exactly the content the
  resolver refuses to serve reach a public comment. Content a direct tool read
  surfaces therefore does not become publishable because this profile exists.
- What this layer does add is that the CLI's own read tools stop being
  auto-denied inside the workspace. That is the intended, minimal grant, and it
  is bounded by path scope, by the deny rules of §4.2, and by the fact that no
  write, command, child-process, Git-mutating, upload, or network tool is
  allowed at all.

If a future requirement needs one of the inexpressible bounds enforced at the
CLI layer, this document changes first.

## 6. Fail-closed refusals

Every refusal is a fixed literal from a closed vocabulary. The literal and its
fixed description are public-safe; the optional detail is local-only.

| Reason | Refused because |
|---|---|
| `workspace-root-not-absolute` | the workspace root is not an absolute path |
| `workspace-root-unrepresentable` | the root cannot be scoped in a rule (glob metacharacters, `..`, trailing separator) |
| `workspace-root-unresolvable` | the root does not resolve to a real directory |
| `settings-path-escapes-workspace` | the settings path resolved outside the workspace |
| `settings-dir-symlink` / `settings-symlink` | `.gemini` or the settings file is a symlink |
| `settings-tracked-by-git` | the settings file is tracked, so it is repository-owned |
| `settings-not-ignored` | the file could not be made Git-ignored |
| `settings-write-verification-failed` | the file did not verify after writing |
| `settings-replaced-before-launch` | the settings pathname no longer named the generated profile when the agent was launched (§1) |
| `workspace-dirty-after-write` | preparation would leave the worktree dirty |
| `workspace-not-trusted` / `workspace-distrusted` | trust is absent, or explicitly refused, for this workspace |
| `trust-store-unreadable` | the global settings document is missing-but-unwritable or not a JSON object |
| `trust-store-inside-workspace` | the global settings document resolves inside the research workspace (§3.4) |
| `git-probe-failed` | a read-only Git check could not run |
| `rule-budget-exceeded` / `operator-glob-budget-exceeded` | the profile exceeds its reviewable size |
| `unvetted-cli-binary` | the agent binary is operator-overridden (§6.1) |
| `schema-drift` | the pinned schema or permission vocabulary no longer matches (§6.2) |
| `cli-version-unreadable` | the installed CLI did not report a parseable version (§6.3) |
| `unsupported-cli-version` | the installed CLI is outside the reconciled version range (§6.3) |
| `global-settings-not-canonical` | a run that launches the CLI was pointed at a store the CLI does not load (§3.5) |
| `global-settings-locked` | another process held the global-store lock past the timeout (§2.5) |
| `global-overlay-contended` | another *workspace's* overlay held the global permission set for the whole wait (§2.5) |
| `global-overlay-journal-damaged` | an overlay journal beside the global store could not be parsed, so the entries it may name can be neither released nor reclaimed (§2.5) |
| `global-overlay-release-failed` | the runner-owned entries could not be removed after the run, so the phase fails rather than reporting a result while they are installed (§2.5) |
| `global-settings-write-failed` | the runner-owned entries could not be written to the global store (§2.5) |

### 6.1 Provenance

The profile is pinned to the vetted CLI's settings dialect. When
`ANTIGRAVITY_BIN` overrides the binary the runner cannot vouch for that dialect,
so it refuses (`unvetted-cli-binary`) rather than writing a permission file it
cannot reason about. This is the same provenance seam the quota classifier
(#671) and the denial classifier (#804) use.

### 6.2 Schema and permission-name drift

Before it is written, every generated document is validated against the pins:
known keys only, known tool names only, allow rules restricted to the allowed
tool set, and every path-bearing rule inside the resolved workspace. An unknown
key, an unknown or renamed tool name, an unscoped allow rule, a rule that
escapes the workspace, or an unknown trust status is a `schema-drift` refusal
with an actionable local detail. Drift never degrades into "write it anyway".

Stated plainly: the runner cannot interrogate the CLI for its current schema, so
this is a *pin*, not a negotiation. Two things follow. First, a CLI that renames
a tool or restructures its settings does not silently gain a broader profile —
the emitted document is fixed and the run either works under it or fails with a
structured `permission-denied/*` outcome (#804) naming the operation class that
was refused. Second, a profile the CLI has stopped understanding shows up as
exactly that outcome with `preparations` recorded in the local artifact, which
is the signal to re-verify the pin here. Because the pin is the only thing
standing between this layer and an unverified permission file, widening it is a
documentation change first.

### 6.3 Installed-CLI version gate (issue #830)

The pin above is necessary but was not sufficient: #826 never confronted it with
the installed binary, so `agy` 1.1.9 could ignore the "verified" profile while
every runner-side check passed. Preparation therefore probes the CLI
(`agy --version`) **before anything is written** and gates the run on the
reconciled range:

| Range | Meaning |
|---|---|
| `>=1.1.9 <2.0.0` | reconciled against this document's schema (`antigravity-cli/settings@3`) |
| anything else | `unsupported-cli-version`, with the observed version and the range in the local detail |
| unparseable / CLI not runnable | `cli-version-unreadable` |

The probe always executes the binary the run is about to launch, and there is no
environment override for it. A `ANTIGRAVITY_CLI_VERSION`-style answer left set
from an earlier session would keep satisfying the gate after the binary was
upgraded or replaced, which is exactly the "verified profile, different CLI"
failure this gate exists to catch. Fixture runs that must not spawn anything
inject the probe (`probeCliVersion`) instead; that injection is test-only, and
it is also what marks a run as launching no CLI (§3.5).

The range is a claim about what has been *tested*, not a guess about what might
work. Widening it means running §11.1's real-CLI smoke test against the new
version and updating this section — in that order.

## 7. Git hygiene

- A **tracked** `.gemini/settings.json` refuses the run. Overwriting it would
  merge the runner into repository content and dirty the worktree.
- If the file is not already ignored, the runner appends a marked,
  root-anchored entry to the repository's own `info/exclude` — local, untracked,
  invisible to `git status`, and idempotent. The entry goes to the **common**
  git directory (`git rev-parse --git-common-dir`), because a linked worktree's
  own `info/exclude` is not consulted. A committed `.gitignore` is never edited.
  The ignore state is then re-probed; still-not-ignored refuses.
- Ignore registration happens **before** the write, so the file never exists as
  an untracked, unignored path even momentarily — but **after** the profile has
  been built and validated (§1), so a configuration that is going to be refused
  never appends the exclude entry.
- After writing, `git status --porcelain -- .gemini/settings.json` must be
  empty. Anything else refuses with `workspace-dirty-after-write`.

## 8. Local artifact and public reporting

`research-workspace-settings.json` in the run artifact directory records the
policy version, the schema pin, the preparation count, the launch-verification
count (§1), whether the global overlay was released (§2.5), the workspace-**relative**
settings path, the content hash and byte length, the pinned tool names, the rule
counts, how the file was ignored, the trust status and which representation it
came from (with the entry *count*, never the entries), the version the installed
CLI reported, and the overlay's rule counts plus how many abandoned overlays it
reclaimed. On a refusal it records the reason literal and its local detail
instead. When the release itself failed it also records `releaseFailure` — the
underlying reason literal and its local detail — which is the operator's handle
on entries that may still be installed.

It never records an absolute path, the rendered rules (which embed the workspace
root), or the file's contents. `research-result.json` carries a compact index:
policy version, content hash, preparation count, and the artifact name.

The published failure string is built from the fixed reason literal and its
fixed description only — never a path, a CLI message, or any settings content.
Structured `permission-denied/*` outcomes (#804) are unchanged: an operation
this profile does not allow is still auto-denied, still classified, and still
reported with bounded local diagnostics.

## 9. Configuration

```jsonc
{
  "research": {
    "antigravity": {
      "workspaceSettings": {
        "enabled": true,            // default false — nothing is written when off
        "registerTrust": false,     // default false — untrusted workspace fails closed
        "globalSettingsPath": "/absolute/path/to/settings.json"  // optional override
      }
    }
  }
}
```

With `enabled` absent or false the research phase writes nothing into the
workspace, installs no global entries, and the invocation path is byte-identical
to before. When absent, `globalSettingsPath` resolves from
`ANTIGRAVITY_CLI_SETTINGS`, then from the user default
`~/.gemini/antigravity-cli/settings.json`. However it is resolved, it must point
outside the research workspace (§3.4), and it is the file the runner-owned
overlay is installed into and removed from (§2.5).

Both settings only move where the *runner* writes. A run that launches the CLI
is refused (`global-settings-not-canonical`) unless they resolve to the store
`agy` itself loads, so neither can quietly decide what the agent may do (§3.5).

One environment variable participates, operator-side:

| Variable | Effect |
|---|---|
| `ANTIGRAVITY_CLI_SETTINGS` | default global store path (§3.4); a real run still requires the canonical store (§3.5) |

## 10. Interaction with #805/#806

- The evidence resolver's bounds, sensitive-path exclusions, output bounds, and
  public/local diagnostic separation remain authoritative. A settings allow rule
  does not bypass them, and this layer adds no evidence source, no operation, no
  denial reason, and no run outcome.
- The evidence-channel instructions still tell the agent to ask for evidence
  through the channel rather than reaching for tools; the profile exists so that
  a tool call the agent makes anyway is bounded and diagnosable instead of
  silently ending the run.
- docs/research-evidence-contract.md §8.7 scopes its "widen agent permissions"
  prohibition to the evidence boundary and points here for this layer.
- The two layers are independently switchable: evidence may run without the
  profile (today's behaviour) and the profile may be prepared for a
  non-evidence run.
- `session.research.evidence.denyGlobs` / `.generatedGlobs` feed **both** layers,
  so the evidence contract's enable-time glob grammar gate (§3.4/§4.6/§4.7 there)
  applies whenever *either* layer is enabled — not only when evidence is. A
  traversal glob such as `../private/**` would otherwise be emitted as a lexical
  `<workspace_root>/../private/**` deny rule that satisfies the profile's
  string-prefix scope check while naming a path outside the workspace; it is
  refused at enable time instead, before any profile is written.

### 11.1 The real-CLI smoke test (opt-in)

`test/antigravity-cli-smoke.test.js` is the check #826 lacked: it drives the
**installed** `agy`, not a stand-in, against committed benign fixtures in a
temporary git workspace, and asserts that

- a `read_file` of the fixture inside the approved workspace succeeds headlessly
  with no interactive prompt and no `permission-denied/*` outcome;
- a **representative research task** over a committed multi-file tree — enumerate
  the files, search for a symbol, read the files that mention it — produces a
  non-empty report naming facts from more than one of them, without requesting a
  command permission, spawning a process, writing, or reaching the network, and
  without leaving the fixture workspace dirty (§2.6, issue #832). This is the
  case a single-file read passed while the real acceptance run failed: the
  earlier smoke proved explicit allow/deny outcomes, not that a research-shaped
  turn stays on the read-only tools;
- the registration itself is in the global store: `tools.core` without any
  command-capable spelling, `tools.exclude` with them, `mcpServers` empty, and
  `autoAccept` false;
- a path outside the approved workspace is not readable;
- write, shell, and network capabilities remain denied;
- the operator's global settings — including unrelated keys and trust entries —
  are byte-for-byte identical once the run releases its overlay.

It is **opt-in**: without `ANTIGRAVITY_CLI_SMOKE=1` it skips, so the normal test
suite never depends on a locally installed CLI. Because it exercises the real
CLI it also uses the real global store (that is the file `agy` reads); the
overlay lifecycle of §2.5 is what makes that safe, and the byte-for-byte
assertion is what proves it. Teardown puts that store back as it was *found* —
the original bytes, or no file at all when there was none — rather than
re-serialising whatever the run left, so the trust entry it registers for its
temporary workspace goes with it and a developer's real configuration is neither
reformatted nor created by running the test. It launches the CLI, so preparation holds it to
that store anyway (§3.5) — a `ANTIGRAVITY_CLI_SETTINGS` left set is refused
rather than quietly turning the test into one that proves nothing.

```bash
ANTIGRAVITY_CLI_SMOKE=1 npx jest test/antigravity-cli-smoke.test.js
```
